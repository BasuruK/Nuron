On the quality rubric alone, this PRD holds up well: it has a genuine thesis (write-time Decision Supersession lineage as the differentiator against Mem0/Cognee), FRs carry testable consequences almost without exception, and the 2026-07-13 Notion-comment reconciliation (nuron-ai split, three-source hybrid retrieval, FR-1/FR-6 confirmations, FR-11 v2 deferral) threads cleanly through every section the rubric dimensions check, leaving only two low-severity mechanical gaps.

The adversarial and edge-case-hunter passes, which stress-test cross-section consistency and boundary conditions rather than dimension maturity, tell a different story about the same 2026-07-13 changes: the nuron-ai/nuron-api service split and the FR-8 retrieval re-scope were reconciled against specific Notion comments and a clarification request, but never checked against the rest of the document the way the original 2026-07-08 draft was. That produced five genuine Critical findings — three blocking contradictions (an "internal Docker network only" claim for nuron-api that conflicts with external API access promised in three other passages; a synchronous-SSE-vs-async-only-RabbitMQ-dispatch conflict between what may be the same "reply"/"query" action; two sections both claiming to "Realize UJ-2" without reconciling agent identity) plus two independently-found structural gaps (GraphRAG's candidate list likely depends on seed entry points from HNSW/BM25, undermining the "three independent sources" framing; the tenant-ID trust boundary is undefined at the internal nuron-api→nuron-ai call). None of this is cosmetic, and none of it should surprise Architecture if resolved now — but it is exactly the class of gap a reviewer-gate pass exists to catch before a PRD is marked final.

Adversarial review

review-adversarial-general.md

The three-source hybrid retrieval clarification is a genuine improvement — no stale two-source language survives anywhere. But the nuron-ai/nuron-api service split introduced a hard contradiction: nuron-api is claimed reachable "only on the internal Docker network" while three other passages assume external callers hit it directly. Layered on top, two sections both claim to answer UJ-2 without saying whether the "query agent" and "Default Agent" are the same thing. Zero new Open Questions were captured from the 2026-07-13 changes despite them touching more architecture surface than the entire 07-08 reviewer gate.

Critical

nuron-api's "internal Docker network only" claim contradicts external API access promised elsewhere

§5.4 vs §2.1, UJ-2, FR-16
§5.4 says nuron-api is Docker-internal-only; the JTBD, UJ-2's entry state, and FR-16's rate-limit language all assume direct external/automation access.
Fix: pick one topology and make every section agree — most likely nuron-api is exposed to ingress while only nuron-ai stays internal.
Critical

FR-9 synchronous SSE streaming contradicts FR-10 async-only RabbitMQ dispatch

§4.4 vs FR-10
If "reply" (FR-10) and "query/answer" (FR-8/FR-9) are the same action, the PRD requires it be both live-streamed and dispatched with no in-process path — no bridge is described.
Fix: confirm whether they're the same action; if so, define the streaming/dispatch bridge (e.g. correlation-ID request/reply with a streaming relay).
Critical

Two sections both claim to "Realize UJ-2" without reconciling agent identity

§4.4 vs §4.5, §5.3
§4.4 attributes UJ-2 to "a synchronous query agent"; §4.5 attributes it to the "Default Agent." §5.3 lists both as distinct components with no stated relationship.
Fix: name the query-answering path exactly once; have the other section reference it.
High

"Neo4j GraphRAG" naming is ambiguous and untracked

Glossary vs Open Question #17
Unclear whether this means integrating Neo4j's own GraphRAG library or is descriptive language for LlamaIndex PropertyGraphIndex retrieval — same risk class as the tracked LangGraph/LlamaIndex ambiguity, but not itself tracked.
Fix: add a line to Open Question #17 asking Architecture to confirm which library implements GraphRAG retrieval.
High

Admin/config handoff across the nuron-ai/nuron-api boundary is undefined

§5.4 vs FR-1, FR-13
Only query delegation is specified between the two services; configuration propagation for ingestion sources and connector settings is not.
Fix: extend §5.4 or Open Question Q-J to explicitly cover config propagation, not just query delegation.
High

"Runtime query agent" is load-bearing but missing from the Glossary

§1, §4.4, §5.3
Every other named agent (Compiler, Curator, Default Agent) has a formal Glossary definition; the query agent does not, obscuring whether it's a fourth distinct agent.
Fix: add a Glossary entry and standardize the name across sections.
Medium

SM-C2 vs. FR-8's degraded-path clause draw a fuzzy "forbidden vs required" line on dropping sources

SM-C2 vs FR-8
Without a concrete timeout threshold, there's no way to audit whether a missing source's contribution was a genuine failure or a latency-motivated skip.
Fix: pin an explicit per-source timeout so "timed out" is a bright line.
Medium

Zero new Open Questions captured from the 2026-07-13 changes

Decision log vs §9
The service split and retrieval re-scope touch as much architecture as the entire 07-08 reviewer gate, yet added no new tracked Open Questions.
Fix: route future architecture-touching changes through the same reviewer-gate discipline as the initial draft.
Medium

FR-17 audit log lacks per-source retrieval provenance

FR-17
The audit log captures cited nodes but not which of HNSW/BM25/GraphRAG surfaced each one, weakening the ability to demonstrate GraphRAG is pulling its weight.
Fix: extend FR-17 to record contributing source(s) per citation, or scope out as v1.1.
Medium

§4.3 conflates initial persistence (FR-5) and scheduled re-curation (FR-7) under a single "Curator" actor

§4.3 vs FR-5, Glossary
The Glossary defines Curator narrowly as the scheduled re-curation agent, while §4.3 also attributes initial persistence to it and FR-5 attributes it to generic nuron-ai.
Fix: state explicitly whether the Curator owns both triggers, or split and name each actor.
Low

"Commodity graph technique" framing sits awkwardly against the bespoke three-source retrieval investment

§1 Vision vs FR-8
The Vision disclaims the graph technique as commodity, yet FR-8 specifies a materially sophisticated, harder-to-replicate retrieval design.
Fix: no v1 action required; revisit the framing if retrieval quality proves a genuine differentiator.

Edge case hunter review

review-edge-case-hunter.md

Fresh pass focused on the two 2026-07-13 changes: the nuron-ai/nuron-api service split and FR-8's three-source hybrid retrieval fusion. 15 findings: 2 Critical, 7 High, 4 Medium, 2 Low. Prior 2026-07-08 gate findings and batched Open Questions were not re-flagged unless the new changes created a materially new variant.

Critical

EC-3.1 — Neo4j GraphRAG's candidate independence assumes seed entry points it may not have

FR-8
Graph traversal typically needs seed nodes; if GraphRAG's seeds derive from HNSW/BM25 output, the "three independent sources" framing FR-8 and SM-C2 rely on isn't achievable as written.
Fix: Architecture must specify GraphRAG's seed-selection mechanism and state whether it can run with zero vector/lexical input.
Critical

EC-5.1 — Tenant-ID trust boundary undefined at the internal nuron-api→nuron-ai call

FR-14, §5.4
FR-14's verified-token-only rule covers the public API only; the actual tenant-scoped query executes inside nuron-ai with no equivalent rule for the internal call.
Fix: extend FR-14's rule to the internal boundary, or require nuron-ai to independently re-validate the tenant claim.
High

EC-2.1 — Supersession fan-out has no reconciliation rule

FR-6, FR-8
One predecessor superseded by two or more unreconciled successors leaves "the present" lineage head undefined during traversal.
Fix: extend FR-6 to trigger on unreconciled fan-out; define traversal behavior at an unresolved fork.
High

EC-2.2 — RTBF deletion of a mid-chain Decision doesn't specify Supersession-edge cleanup

FR-15, FR-8
Deleting a mid-chain node risks a dangling edge or untraceable gap during lineage traversal, with no defined fallback.
Fix: define whether deletion bridges the chain around the gap or truncates traversal with an explicit "lineage incomplete" marker.
High

EC-3.2 — Vector/lexical-only degradation can silently drop Supersession lineage from an answer

FR-8
A generic degraded-path marker doesn't distinguish "lineage context specifically was missing" from any other source dropping out.
Fix: require the degraded-path record to explicitly flag when lineage retrieval was skipped.
High

EC-3.3 — No cross-source deduplication rule before RRF fusion

FR-8
HNSW and GraphRAG can surface the same node independently; without a stated dedup rule, fused ranking becomes non-deterministic.
Fix: define dedup-by-node-ID as a pre-fusion step with a rank-precedence rule.
High

EC-3.4 — No defined behavior for simultaneous multi-source failure

FR-8
Two-of-three or all-three sources failing at once has no stated response contract.
Fix: define a minimum-surviving-sources threshold below which the query fails explicitly.
High

EC-5.2 — nuron-ai crash/restart mid-query isn't covered by any stated contract

FR-9, §5.1
Restart-safety NFR is scoped only to the async pipeline (FR-4), leaving the synchronous query/SSE path's restart behavior undefined.
Fix: extend restart-safety guarantees, or define a distinct contract, for the synchronous query path.
High

EC-5.5 — RTBF cascade has no defined behavior if nuron-ai is unreachable during deletion

FR-15
No stated retry/queuing contract risks nuron-api-side data purged while nuron-ai's graph data survives, violating the deletion guarantee.
Fix: require the deletion operation to durably queue the nuron-ai-side cascade and confirm completion before considering it done.
Medium

EC-3.5 — No RRF tie-breaking rule

FR-8
Ties in fused RRF score have no stated deterministic resolution.
Fix: pin a deterministic tie-break alongside the RRF constant deferred to Open Question #17.
Medium

EC-4.1 — "Reply" (async) vs. "query" (synchronous) path ambiguity

FR-10, FR-8
The two mechanisms could diverge in retrieval logic or error handling without anyone noticing.
Fix: state explicitly whether they're the same logical operation via different transports.
Medium

EC-5.3 — Cross-service config propagation for nuron-ai-side settings is unspecified

FR-13
Unclear whether retrieval/LLM/embedding config is pushed, polled, or configured directly in nuron-ai out of band.
Fix: clarify in Architecture which service owns which config surface and how changes propagate.
Medium

EC-5.4 — Per-tenant rate limiting doesn't protect nuron-ai's shared capacity

FR-16
Many tenants individually within quota could collectively saturate nuron-ai's shared compute with no aggregate throttle.
Fix: consider a concurrency/queue-depth cap on nuron-ai independent of the per-tenant limiter.
Low

EC-1.1 — No canonical tag vocabulary for the Tags block

FR-2, FR-8
Tag drift silently degrades the BM25/Tags fusion source's consistency over time.
Fix: define a canonical tag taxonomy or synonym-folding step at structuring time.
Low

EC-5.6 — Audit trail doesn't specify per-source provenance across the three retrieval sources

FR-17
Found independently of the adversarial reviewer's identical FR-17 finding — a convergent signal.
Fix: include per-source contribution (pre- and post-fusion rank) in the audit record.
